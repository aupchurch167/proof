# A3 — Data durability

**Exec summary.** Uploads are on DigitalOcean Spaces (not droplet disk) — do not “move them to the droplet.” There is **no restore runbook** and no Neon/PITR mention in the repo. Vendor delete **hard-deletes** every COI row and the PDF objects. Cron is in-process and will silently skip a day if the Node process is down at 08:00. Draft runbook: `/audit/restore-runbook-draft.md`.

Honest RPO/RTO from evidence: **unknown**. If Neon PITR is on with default 7-day window, RPO ≈ minutes, RTO ≈ hours for DB; Spaces versions (if enabled) are independent. If neither exists, RPO = time since last unknown snapshot, RTO = rebuild from nothing.

ID:          A3-01
Title:       No tested backup/restore path in the repo
Severity:    High
Evidence:    Grep `neon|PITR|backup` across `*.md,*.js,*.json`: only `docs/migrations.md:61` “Take a database backup before baselining.” No runbook, no snapshot script, no `pg_dump` notes, no Spaces versioning note.
Impact:      A bad `migrate deploy`, a dropped Neon branch, or a stolen/rotated Spaces key without object-lock means customer COIs (the product) are gone. Pre-launch, this is the difference between an incident and a company-ending event.
Fix sketch:  Owner confirms Neon PITR + PITR test restore to a branch. Enable Spaces versioning. Fill `/audit/restore-runbook-draft.md` with real project IDs. Rehearse once.
Effort:      M (owner + one engineer)
Test:        Restore yesterday 15:00 to a Neon branch; `prisma migrate diff` clean; signed URL for one known pdfPath works.

ID:          A3-02
Title:       Vendor delete hard-deletes COIs and Spaces objects
Severity:    High
Evidence:    `vendors.js:278-320` (bulk) and `322-360` (single): `deleteFile` each `pdfPath`, then `prisma.coi.deleteMany`, then `vendor.update({ deletedAt })`. No recycle bin, no `deletedAt` on Coi, no confirmation token bound to vendor count. UI checklist asks for a confirm modal (`docs/testing-checklist.md:13-14`) — that is client-only.
Impact:      MEMBER (`authorize('ADMIN','MEMBER')`) can wipe an org’s certificate history and the blobs in one call. Cascade from Coi also drops related NotificationLog.fk? NotificationLog.coi is optional without `onDelete: Cascade` in schema (`schema.prisma:246-247` — relation has no onDelete, Prisma default Restrict) — bulk delete may **500** if logs point at those COIs, or succeed if no logs. Either data loss or a broken delete.
Fix sketch:  Soft-delete COIs; do not `deleteFile` until a retain-for-period window (`organization.coveragePeriod.retainForPeriod` already exists as a flag and is unused for retention). Wrap delete in `$transaction`. Files: `schema.prisma`, `routes/vendors.js`, `services/compliance.js`.
Effort:      M
Test:        Vendor with COI + notificationLog: DELETE vendor → 200, COI still gettable by ADMIN with `includeDeleted`, Spaces object still exists.

ID:          A3-03
Title:       Organization onDelete: Cascade wipes the tenant
Severity:    High
Evidence:    `schema.prisma:118,138,165,223,245,264,287,310,334` — Settings, User, Vendor, Coi, NotificationLog, AuditLog, ApiClient, CoiRequest, WebhookEndpoint all `onDelete: Cascade` from Organization. No `DELETE /api/organization` route today (good), but any operator `prisma.organization.delete` or a future “close account” button is irreversible and unlogged at the platform level.
Impact:      Support/debug `delete` on the wrong org is total customer loss, including audit trail.
Fix sketch:  Change to `Restrict` + an explicit offboarding job that exports then soft-deletes. Never cascade audit logs. File: `schema.prisma` + migration (non-trivial).
Effort:      L
Test:        `organization.delete` with children → FK error. Offboarding job covered by a runbook test.

ID:          A3-04
Title:       Cron jobs are in-process and not durable
Severity:    High
Evidence:    `index.js:12-17` starts four `CronJob`s in the web process. `cron.js:284-297` expiration at `0 8 * * *`. No job row, no advisory lock, no catch-up on boot (`runExpirationSweep` is only invoked by the cron callback, not at startup). Token refresh Sunday midnight (`317-341`) is what expires portal links in practice (A1-13).
Impact:      Deploy or OOM at 08:00 → no reminders that day (window logic **does** catch up the next successful run — `cron.js:40-43` — so expiration is resilient; **token refresh is not**). Two Node processes (PM2 cluster, accidental double start) double-email every vendor.
Fix sketch:  External scheduler (systemd timer / GitHub Action / deferred Neon job) calling authenticated internal routes, or a `CronLock` table (`UPDATE ... WHERE lockedAt < now()-23h`). Run sweep on boot if last success > 26h. Files: `services/cron.js`, new lock model.
Effort:      M
Test:        Two overlapping `runExpirationSweep` calls → second is a no-op. Kill process at 07:59, restart 08:05, sweep still runs.

ID:          A3-05
Title:       Outbound webhooks are single-attempt
Severity:    Medium
Evidence:    `webhookDispatcher.js:10,18-45,69-70` — 5s timeout, one POST, status recorded, “callers should not await this on a critical path.”
Impact:      Quill (or any consumer) misses `coi.updated` on a 502. They must poll. Fine for beta, not for “source of truth” integrations.
Fix sketch:  Delivery table + retry 1m/10m/1h. File: `webhookDispatcher.js`, new model.
Effort:      M
Test:        First fetch throws; second attempt within 2m succeeds; `lastDeliveryStatus=success`.

ID:          A3-07
Title:       Import-created vendors keep schema-default UUID upload tokens; writes are not transactional
Severity:    Medium
Evidence:    `import.js:148-158` `vendor.create` without `generateUploadToken`. Comments elsewhere say UUID tokens 404 on the portal — they do **not** (A1-13); they work forever. Vendor delete (`vendors.js:292-311`) is sequential awaits, not `$transaction`. Signup **is** transactional (`auth.js:32-58`).
Impact:      Partial bulk delete: PDFs gone, rows remain (or vice versa). Imported vendors have non-rotating portal secrets until Sunday cron.
Fix sketch:  Call `generateUploadToken` in import create. Wrap delete file+rows in a transaction; delete blobs after commit (or accept orphan blobs). Files: `import.js`, `vendors.js`.
Effort:      S
Test:        Imported vendor `uploadToken` matches JWT shape. Kill Spaces mid-bulk-delete → no row deleted.

## Done well (do not “fix”)

- Blobs are on Spaces with private ACL and UUID keys (`storage.js:29-41`) — **not** on the droplet. Do not move them local.
- Coverage amounts are Int cents (`schema.prisma:99-101`, import `toCents`).
- Signup org+user is `$transaction` (`auth.js:32`).
- v1 COI-request create is idempotent-ish (`v1/vendors.js:235-243`).
- Expiration reminder windows are catch-up safe (`cron.js:40-43`).
- `docs/migrations.md` is honest about `db push` drift and has an idempotent reconcile migration.
- Graceful HTTP shutdown + `prisma.$disconnect` (`index.js:20-36`).
