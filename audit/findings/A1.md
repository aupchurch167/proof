# A1 — Authentication and sessions

**Exec summary.** Password hashing is fine (bcrypt cost 12). Session design is not: JWTs live in `localStorage`, refresh tokens are stateless and unrevocable for 7 days, email verification is cosmetic, Google will attach to any existing row with the same email, and invite links never expire. `verifyUploadToken()` — the only function that would enforce portal JWT expiry — is dead code.

---

ID:          A1-01
Title:       Refresh tokens cannot be revoked; logout is localStorage-only
Severity:    High
Evidence:    `server/src/utils/tokens.js:11-16` signs a 7-day refresh JWT with only `{id, orgId}`. `server/src/routes/auth.js:228-249` verifies it and mints a **new** pair without a jti, denylist, or stored family. `client/src/contexts/AuthContext.jsx:49-53` logout only `removeItem`s tokens. There is no Session / RefreshToken table in `schema.prisma`.
Impact:      A stolen refresh token (XSS, shared laptop, backup of localStorage) works for 7 days after the user clicks Log out, after a password change, and after an admin removes the user (until the next refresh call — `/refresh` does check `user` still exists, but password reset does not rotate a server-side session). Password reset (`auth.js:463-467`) clears `resetToken` only.
Fix sketch:  Persist refresh tokens (hash + family + expiry) on User or a Session table; rotate and revoke the family on logout, password reset, and user delete. Add `POST /api/auth/logout` that authenticates and deletes the family. Files: `schema.prisma`, `routes/auth.js`, `utils/tokens.js`, `AuthContext.jsx`.
Effort:      M
Test:        Login, capture refresh token, logout, assert `/auth/refresh` returns 401. Reset password, assert old refresh 401.

ID:          A1-02
Title:       Email verification is never enforced on any API route
Severity:    High
Evidence:    Signup issues tokens immediately (`auth.js:63-79`) with `emailVerified: false`. Grep of `server/src` shows `emailVerified` is read only to return it or to set it true — never as a gate. Banner copy claims “unlock all features” (`client/src/components/EmailVerificationBanner.jsx:23`) but `PrivateRoute` only checks `user` (`App.jsx:27-31`).
Impact:      Anyone can sign up with a victim’s email, operate a full tenant (create vendors, request COIs that email the victim’s vendors if they type them, generate API keys if they stay ADMIN), and block the real owner from registering that address (`User.email @unique`).
Fix sketch:  Middleware `requireVerified` on all non-auth routes (or allow a “verify-only” allowlist). Do not issue tokens until verify, or issue a restricted token. Files: `middleware/auth.js`, `app.js`, `routes/auth.js`.
Effort:      S
Test:        Signup, call `GET /api/vendors` before clicking verify → 403. After `GET /api/auth/verify-email?token=` → 200.

ID:          A1-03
Title:       Google sign-in links by email to unverified password accounts
Severity:    High
Evidence:    `auth.js:153-173` `findFirst({ OR: [{ googleId }, { email: profile.email }] })` then writes `googleId` and `emailVerified: true`. Password signup does not prove email (`auth.js:46-54`). `PUT /api/auth/me` can change email with no verification (`auth.js:365-371`).
Impact:      (1) Attacker signs up as `owner@gc.com`. Real owner later clicks “Continue with Google” and is dropped into the attacker’s tenant (or the attacker later Google-logins into a tenant whose admin changed their email to a Google address they do not control — wait: Google login requires the Google account). Concrete takeover: attacker changes their email to a victim Gmail they do not own (`PUT /me`), victim cannot sign up; if the victim already had a password account at that Gmail and it was unverified, Google login hijacks that row. More likely product bug: a contractor using a shared inbox cannot recover the intended org. Combined with A1-02 this is how an unverified signup becomes a durable identity.
Fix sketch:  Only link Google → existing user if `emailVerified === true` or `googleId` already matches. Treat email change as pending until re-verified. Files: `routes/auth.js`.
Effort:      S
Test:        Create password user `a@gmail.com` unverified. Google login as `a@gmail.com` must 409/403, not return that user’s tokens.

ID:          A1-04
Title:       Invite tokens never expire, are UUID v4, and are returned by GET /users
Severity:    High
Evidence:    `users.js:42-55` `inviteToken = uuidv4()`, stored plaintext, no expiry column. `GET /api/users` selects `inviteToken` (`users.js:16`). `accept-invite` (`auth.js:284-291`) accepts any still-present token. Compare reset tokens: 32-byte hex + 1h (`auth.js:425-426`).
Impact:      Any ADMIN response, browser extension, or XSS that sees `/api/users` can mint a teammate account. A forwarded invite email works forever. UUID v4 is 122 bits — entropy is OK; **non-expiry + API echo** is the issue.
Fix sketch:  Stop returning `inviteToken`. Hash it at rest (like API tokens). Add `inviteTokenExpiry` (48h). Files: `routes/users.js`, `schema.prisma`, `routes/auth.js`.
Effort:      S
Test:        `GET /api/users` body must not contain `inviteToken`. Accept after expiry → 404.

ID:          A1-05
Title:       JWT_SECRET and JWT_REFRESH_SECRET are not validated at process boot
Severity:    High
Evidence:    `server/src/index.js` listens then starts crons; no check. `tokens.js:4-16` passes `process.env.JWT_SECRET` / `JWT_REFRESH_SECRET` straight to `jwt.sign`. If unset, `jsonwebtoken` signs with `undefined` (or throws inconsistently across versions). No `envalid`/`zod` boot schema exists (grep `process.env` in `index.js` / `app.js`).
Impact:      A mis-deployed process can issue or accept tokens with a weak/empty secret, or crash on first login with a useless log line. Two environments sharing a default would let tokens cross.
Fix sketch:  At the top of `index.js`, exit 1 unless both secrets are ≥32 bytes of entropy and not the `.env.example` placeholders. File: `server/src/index.js` (new `src/config/env.js`).
Effort:      S
Test:        Start server with JWT_SECRET unset → process exits nonzero before listen.

ID:          A1-06
Title:       Signup and invite enumerate registered emails
Severity:    Medium
Evidence:    `auth.js:24-27` signup returns 409 `'Email already registered'`. `users.js:37-40` invite same. Forgot-password correctly always 200 (`auth.js:422-437`). Timing still differs (hash vs no user) on login but messages are generic (`auth.js:96-111`).
Impact:      An unauthenticated caller can confirm whether a GC’s email is a Proof customer.
Fix sketch:  Signup/invite: same generic 200/201 + email (“if this address is new, we sent a link”). Or keep 409 only for authenticated invite inside an org. Files: `routes/auth.js`, `routes/users.js`.
Effort:      S
Test:        Signup existing vs new email → identical status + timing ±50ms.

ID:          A1-07
Title:       Access and refresh tokens are stored in localStorage
Severity:    Medium
Evidence:    `client/src/utils/api.js:8-13,24-35` and `AuthContext.jsx:27-28`. Cookies are not used; no `HttpOnly`/`Secure`/`SameSite`.
Impact:      Any XSS (including a future markdown/email HTML hole, or a compromised GIS script allowed by CSP `script-src` GIS) steals a 7-day refresh token. CSP does allow `'unsafe-inline'` styles and Google GIS (`app.js:41-51`).
Fix sketch:  Move refresh to an `HttpOnly; Secure; SameSite=Strict` cookie on the API origin; keep access in memory. Files: `app.js` (cookie parser), `routes/auth.js`, `api.js`.
Effort:      M
Test:        After login, `document.cookie` has no refresh; DevTools Application → localStorage has no refreshToken.

ID:          A1-08
Title:       No MFA on ADMIN (or any role)
Severity:    Medium
Evidence:    Schema User has no TOTP/WebAuthn fields. Auth routes have login/google/refresh only. `docs/testing-checklist.md` has no MFA item.
Impact:      A phished ADMIN password (or Google session) is full tenant control including API keys (`/api/integrations`).
Fix sketch:  TOTP for ADMIN before integrations + user invite. File set: schema + `routes/auth.js` + settings UI.
Effort:      L
Test:        ADMIN without TOTP enrollment is challenged on `/api/integrations/*`.

ID:          A1-09
Title:       Accept-invite does not mark emailVerified
Severity:    Medium
Evidence:    `auth.js:295-304` updates firstName/lastName/passwordHash/inviteToken=null only. Invited user is then fully authenticated (`306-320`) with no `emailVerified: true`.
Impact:      Combined with a future verify-gate (A1-02 fix), invited teammates would be locked out. Today it just means the banner stays up for people who proved inbox control via the invite link.
Fix sketch:  Set `emailVerified: true` on accept. File: `routes/auth.js`.
Effort:      S
Test:        Accept invite → `GET /api/auth/me` has `emailVerified: true`.

ID:          A1-10
Title:       Seed script prints a real-looking production password
Severity:    Low
Evidence:    `server/prisma/seed.js:7,23-30,193` `bcrypt.hash('password123', 12)` for `admin@markallancont.com`.
Impact:      If seed was ever applied to the production DB (open question), that password is in git forever. Even if not, it trains operators to use it locally and copy-paste.
Fix sketch:  Read seed password from env; refuse to run when `NODE_ENV=production`. File: `prisma/seed.js`.
Effort:      S
Test:        `NODE_ENV=production node prisma/seed.js` exits 1.

ID:          A1-11
Title:       PUT /api/auth/me skips the updateProfile zod schema
Severity:    Medium
Evidence:    `validation.js:30-36` defines `updateProfile` (email format + password rules). `auth.js:352` uses `authenticate` only. Email uniqueness is checked; format is not. `newPassword` uses `passwordSchema` (`373-378`); email/name do not.
Impact:      Stored non-emails break invite/login uniqueness; no current-password required to change email.
Fix sketch:  `router.put('/me', authenticate, validate('updateProfile'), ...)`. Require current password (or Google reauth) to change email; set `emailVerified=false` and issue a new verify token. File: `routes/auth.js`.
Effort:      S
Test:        PUT `{email:'not-an-email'}` → 400. PUT email without currentPassword → 400.

ID:          A1-12
Title:       jwt.verify does not pin algorithms
Severity:    Low
Evidence:    `middleware/auth.js:11`, `tokens.js:28`, `auth.js:236` call `jwt.verify(token, secret)` with no `{ algorithms: ['HS256'] }`.
Impact:      With a string secret, `jsonwebtoken` ≥9 rejects `none` and asymmetric algs in most versions; still a one-line hardening miss if the library default changes.
Fix sketch:  Pass `{ algorithms: ['HS256'] }` on every verify. Files: `middleware/auth.js`, `utils/tokens.js`, `routes/auth.js`.
Effort:      S
Test:        Token with `alg: none` → 401.

ID:          A1-13
Title:       Portal upload JWTs are not verified; 7-day expiry is fiction
Severity:    High
Evidence:    `utils/tokens.js:19-33` `generateUploadToken` / `verifyUploadToken` (jwt, purpose=upload, 7d). Grep: `verifyUploadToken` is **exported and never imported** by any route. Portal (`portal.js:30-31,77-78,106-107`) is `findFirst({ uploadToken: req.params.uploadToken })`. Comments in `vendors.js:511-514` and `cron.js:22-25` claim “the portal can't jwt.verify()” UUID tokens — the portal never jwt.verify()s anything. Weekly cron (`cron.js:317-337`) is the only rotation.
Impact:      A leaked portal URL (email forward, `GET /api/vendors` dump, sidebar “Vendor portal” link) works until Sunday midnight **or** the next request-coi, even if the JWT `exp` is past. Import-created vendors keep the schema default UUID forever if cron/request never run.
Fix sketch:  Call `verifyUploadToken` in all three portal handlers; 401 on expiry/purpose mismatch; still look up vendor by `id` from the payload (not by raw token string). Files: `routes/portal.js`.
Effort:      S
Test:        Mint token, expire it (`jwt.sign` with `expiresIn: '0s'` stored on vendor), GET portal → 401. UUID token → 401.

## Done well (do not “fix”)

- bcryptjs cost 12 (`auth.js:29,109,293`).
- Forgot-password anti-enumeration (`auth.js:422-437`).
- Auth endpoints rate-limited 10/15m (`app.js:115-120`).
- `trust proxy` set to 1 so rate-limit keys work behind Nginx (`app.js:32`).
- Google ID token audience + `email_verified` check (`lib/google.js:17-28`).
- API v1 tokens stored as SHA-256, shown once (`lib/apiTokens.js`, `routes/integrations.js:91`).
- Last-admin protection on role change and delete (`users.js:89-97,128-136`).
- Invite role allowlist is only ADMIN|MEMBER (`users.js:34-35`) — cannot self-assign REVIEWER/VIEWER via invite.
