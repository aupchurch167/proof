# A6 — Reliability and observability

**Exec summary.** There is no Sentry (or any error tracker). Logs are `console.log`/`morgan`. `/api/health` exists and pings Postgres. Graceful HTTP shutdown is implemented; cron jobs are not stopped. Outbound `fetch` to Core and inbound attachment URLs has **no timeout**. Hottest list endpoints are unpaginated. Load scripts: `/audit/load/`.

---

ID:          A6-01
Title:       No error tracking product
Severity:    High
Evidence:    Grep `Sentry|sentry|datadog|newrelic|pino|winston` across the repo: **no matches**. Errors go to `console.error` (e.g. `app.js:171`, every route catch).
Impact:      A production 500 on COI approve or a cron throw is visible only if someone is watching `pm2 logs` at that second. Launch without this is flying blind.
Fix sketch:  `@sentry/node` + `@sentry/react`. Capture Express errors in the existing handler. File: `app.js`, `client/src/main.jsx`.
Effort:      S
Test:        Throw in a test route; event appears in Sentry project.

---

ID:          A6-02
Title:       Core and inbound-attachment fetch have no timeout
Severity:    High
Evidence:    `lib/core.js:31-37` `fetch(url, { method, headers, body })` — no `AbortSignal`. `webhooks.js:98` `fetch(att.url)` — no signal. Contrast: outbound webhooks use 5s AbortController (`webhookDispatcher.js:19-20`).
Impact:      A hung Core or a slow SSRF target pins a Node request (and the inbound webhook handler) indefinitely. One slow Resend retry storm (webhook is **not** rate-limited — `app.js:65-67`) saturates the event loop.
Fix sketch:  Shared `fetchWithTimeout(url, opts, 5000)`. Files: `lib/core.js`, `routes/webhooks.js`.
Effort:      S
Test:        nock a delayed Core → function rejects at 5s.

---

ID:          A6-03
Title:       Logs are unstructured console + morgan
Severity:    Medium
Evidence:    `morgan` combined in production (`app.js:78`). Cron logs vendor **email** (`cron.js:119`). Webhook logs inbound payload slices (`webhooks.js:213,229`). Email logs full recipient (`email.js:38`).
Impact:      Cannot query “all 5xx for org X.” PII in logs (emails, payload previews) expands the compliance surface (A10).
Fix sketch:  pino JSON with `orgId`/`reqId`; redact email. File: new logger, replace console in routes incrementally.
Effort:      M
Test:        One request produces a single JSON line with `reqId` and no raw email.

---

ID:          A6-04
Title:       Graceful shutdown does not stop cron
Severity:    Medium
Evidence:    `index.js:20-36` closes HTTP + Prisma, 10s force exit. CronJob `.stop()` is never called. A sweep mid-email can be killed after 10s.
Impact:      Deploy during 08:00 sweep → partial NotificationLog (sent email, no row, or row without send).
Fix sketch:  Keep a `running` flag; `job.stop()`; wait for in-flight sweep; then `server.close`. File: `index.js`, `cron.js`.
Effort:      S
Test:        SIGTERM during a mocked long sweep waits, then exits 0.

---

ID:          A6-05
Title:       Hottest GETs are unpaginated and reminders N+1
Severity:    Medium
Evidence:    `GET /api/vendors` `findMany` all vendors + all their COIs (`vendors.js:65-79`) — then slices to 1 COI in JS. `GET /api/cois` all COIs (`cois.js:80-87`). `GET /api/reminders/upcoming` loads every vendor with notifications, then `await prisma.coi.count` **inside the loop** (`reminders.js:104-106`). v1 vendors **are** cursor-paginated (`v1/vendors.js:78-101`).
Impact:      An UNLIMITED org with a few thousand vendors will stall the single-thread process on every dashboard load (Layout also polls `/reports/compliance` every 120s — `Layout.jsx:62-64`).
Fix sketch:  Add `take`/`cursor` to session vendor/COI lists (same helper as v1). Batch the reminder counts. Files: `routes/vendors.js`, `cois.js`, `reminders.js`.
Effort:      M
Test:        1k vendors: GET /vendors `?limit=50` returns 50 + cursor. Reminders: one query for all counts.

---

ID:          A6-06
Title:       Uptime alert and email DNS not evidenced
Severity:    Unverified
Evidence:    Health route exists (`app.js:152-159`). No Better Uptime / Pingdom / PagerDuty config. `.env.example:13-14` tells the operator to set DKIM/SPF/DMARC in Resend — not verified from here.
Impact:      If health is not monitored, customers find out Proof is down. If SPF fails, COI request emails land in spam and vendors never upload.
Fix sketch:  Owner: healthcheck 60s + SMS. Resend dashboard: all three green. Record in server-checklist.
Effort:      S (owner)
Test:        Stop PM2 → phone page in <5m. Mail-tester.com 8/10+ on a request-coi.

---

ID:          A6-07
Title:       Health endpoint is the only probe; no separate liveness/readiness
Severity:    Low
Evidence:    Single `/api/health` that 503s if DB is down. A deploy that blocks on Prisma will mark the instance dead (good) but Nginx has no `max_fails` in `proof.conf`.
Impact:      Operational polish. Not a customer-facing bug today.
Fix sketch:  `/live` (process up) vs `/ready` (DB). File: `app.js`, Nginx.
Effort:      S
Test:        Stop Postgres → `/live` 200, `/ready` 503.

## Done well

- `trust proxy`, helmet, combined morgan in prod.
- HTTP graceful shutdown + 10s fuse (`index.js:20-36`).
- Outbound customer webhooks already time out at 5s.
- Health checks the database, not just `res.json({ok:true})`.
- v1 list endpoints already paginated (do not “simplify” them).
