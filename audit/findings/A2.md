# A2 — Authorization and tenant isolation

**Exec summary.** Browser-session queries almost always include `orgId: req.user.orgId`. The v1 API has real two-tenant tests. The holes that matter for launch are **not** missing `where` on `/api/vendors/:id` — they are **shared-email inbound webhooks**, **optional webhook auth**, **Core mirroring every tenant into one Core org**, and **portal tokens sitting on authenticated GETs**. There is no structural defense (RLS / Prisma extension).

ID:          A2-01
Title:       Inbound Resend webhook attaches replies and COIs to every vendor sharing an email, across tenants
Severity:    Critical
Evidence:    `webhooks.js:232-269`:
```
const matches = await prisma.vendor.findMany({
  where: { email: fromEmail, deletedAt: null },
  select: { id: true, orgId: true, name: true },
});
for (const v of matches) { ... processAttachment ... auditLog.create({ orgId: v.orgId ... }) }
```
No `orgId` predicate. Two GCs with the same subcontractor email both receive the PDF and a `vendor_reply` audit row. Bounce handler (`288-296`) picks the latest SENT `NotificationLog` for that recipient **with no org filter**.
Impact:      Cross-tenant data write and document bleed. A sub who works for two Proof customers can have Tenant B’s inbound PDF filed on Tenant A’s vendor (and vice versa). Bounce can flip the wrong tenant’s notification to FAILED.
Fix sketch:  Match on `(email, orgId)` derived from the original outbound (`In-Reply-To` / custom header / per-org Reply-To). Never `findMany` vendors by email globally. Files: `routes/webhooks.js`, email `Message-ID` when sending (`services/email.js`).
Effort:      M
Test:        Two orgs, same vendor email. POST inbound (signed). Assert only the org that sent the last UPLOAD_REQUEST gets the Coi + audit row. See `/audit/tenant-isolation-tests.md` case WH-1.

ID:          A2-02
Title:       Inbound webhook authentication is optional
Severity:    Critical
Evidence:    `webhooks.js:186-189`:
```
if (process.env.RESEND_WEBHOOK_SECRET && !verifySvixSignature(...)) return 401;
```
`.env.example:21-23` says “Leave blank in dev.” Route is mounted **before** the rate limiter (`app.js:65-75`). Combined with A2-01 and A4-01 (SSRF on `att.url`).
Impact:      If production secret is unset (open question), anyone on the internet can create PENDING_REVIEW COIs and AuditLogs for every vendor whose email they know, and trigger server-side `fetch(att.url)`.
Fix sketch:  Require `RESEND_WEBHOOK_SECRET` when `NODE_ENV=production` (boot-fail). Always verify. Files: `index.js` env check, `webhooks.js:186`.
Effort:      S
Test:        Unset secret + NODE_ENV=production → process exits. Set secret, POST without Svix headers → 401. Unsigned body never creates rows.

ID:          A2-03
Title:       Helm Core mirror sends every tenant’s vendors to a single CORE_ORG_SLUG
Severity:    Critical
Evidence:    `lib/core.js:12-16,70-87` — `createVendor` POSTs to `/api/v1/orgs/${CORE_ORG_SLUG}/vendors` with `x-helm-test-user-id` / `x-helm-test-org-slug` (comment: “Dev-bypass auth — no real auth yet”). `vendors.js:144-156` `mirrorCreateToCore` runs on **every** create when `HELM_CORE_INTEGRATION === 'true'`, with no check that `req.user.orgId` matches a dedicated Helm org. Same for import (`import.js:175-188`) and compliance status (`compliance.js:165-171`).
Impact:      If the flag is on in production, Vendor PII (name, email, phone, address, trade) from **all** Proof customers is written into one Core organization. Comment in `.env.example:44` admits “no real auth yet.”
Fix sketch:  Gate mirror on `vendor.orgId === configuredProofOrgId`. Default the flag off. Do not use test-bypass headers in production. Files: `lib/core.js`, `routes/vendors.js`.
Effort:      S
Test:        Enable integration with CORE_ORG_SLUG=mac; create vendor in a second org; assert `core.createVendor` is not called (spy).
Unverified:  Whether the flag is actually true in production — owner must confirm. If false, severity in production is latent.

ID:          A2-04
Title:       Any authenticated org member receives live vendor portal tokens
Severity:    High
Evidence:    `GET /api/vendors` returns full Vendor rows including `uploadToken` (`vendors.js:65-92` spread). Create vendor response includes it (`137`). `GET /api/organization/usage` returns `portalPreviewToken: sampleVendor?.uploadToken` (`organization.js:63-83`) for **any** role. Layout renders it as “Vendor portal ↗” (`Layout.jsx:116-126`). Portal PUT `/info` and POST `/upload` are unauthenticated beyond the token (`portal.js:72-103`).
Impact:      A VIEWER or a compromised MEMBER session can open the first vendor’s portal, rename them, change their email, and upload certificates — bypassing `authorize()`. Tokens also ride along in every vendor list JSON (XSS → all portal URLs).
Fix sketch:  Never return `uploadToken` from session APIs. Usage endpoint should not expose it; use a dedicated ADMIN-only preview that mints a short-lived purpose token. Files: `routes/vendors.js` (select/omit), `routes/organization.js`, `Layout.jsx`.
Effort:      S
Test:        MEMBER `GET /api/vendors` → no `uploadToken` key. `GET /api/organization/usage` → no `portalPreviewToken` for non-ADMIN.

ID:          A2-05
Title:       Public apply accepts org UUID and creates vendors without a plan limit
Severity:    High
Evidence:    `apply.js:34-38` `OR: [{ slug }, { id }]`. `GET /api/organization` returns the full row including `id` and `slug` to any role (`organization.js:9-19`). Settings UI publishes `/apply/${org.slug || org.id}` (`Settings.jsx:56,214-216`). POST creates a Vendor (`apply.js:92-105`) **without** `enforcePlanLimit('vendor')`. Rate limit is 20/hour/IP (`26-32`).
Impact:      Knowing an org UUID (leaked from any authenticated session, HAR file, or support transcript) lets a stranger fill that tenant with vendors and PDFs, burning Anthropic spend (A4-04) and the COI plan quota. Slug-or-id is also how v1 resolves orgs (`apiAuth.js:22-26`) — fine for authenticated tokens, not for a public form.
Fix sketch:  Resolve apply **only** by non-null `slug`. Refuse apply when slug is missing. Call the same plan-limit logic as POST /vendors. Files: `routes/apply.js`, `middleware/planLimits.js`.
Effort:      S
Test:        POST `/api/apply/<uuid>` → 404. POST `/api/apply/<slug>` at FREE cap → 403 PLAN_LIMIT_EXCEEDED.

ID:          A2-06
Title:       No structural tenant defense (Prisma extension or RLS)
Severity:    Medium
Evidence:    `lib/prisma.js` is a bare `new PrismaClient`. Schema has no RLS policies (grep `ENABLE ROW LEVEL SECURITY` in `server/prisma/migrations` is empty). Isolation is by developer discipline. A2-01 is the proof that discipline failed once.
Impact:      The next `findMany({ where: { email } })` or `findUnique({ where: { id } })` will be a cross-tenant bug. Reviewers have no mechanical backstop.
Fix sketch:  Prisma client extension that forbids Vendor/Coi/User queries without `orgId` unless an explicit `bypassTenant` symbol is passed (used only by cron/webhooks with a documented org). Longer term, Postgres RLS on `org_id`. Files: `lib/prisma.js`, migrations.
Effort:      L
Test:        Unit test: `prisma.vendor.findMany({ where: { email } })` throws. Cron uses the bypass.

ID:          A2-07
Title:       VIEWER (and REVIEWER) are first-class in the schema but unused in invite; VIEWER would see all PII
Severity:    Medium
Evidence:    `UserRole` includes REVIEWER, VIEWER (`schema.prisma:10-15`). Invite and role-change allow only ADMIN|MEMBER (`users.js:34-35,77`). Almost every GET is `authenticate` only. A VIEWER created via Prisma studio or a future UI change inherits A2-04.
Impact:      Role names in the JWT (`tokens.js:5`) will be trusted by `authorize()` but GETs never call it. “Viewer” is not a viewer.
Fix sketch:  Either delete VIEWER/REVIEWER from the enum or apply `authorize` on every mutating route (already mostly done) **and** strip tokens/PII on VIEWER GETs. Files: `middleware/auth.js` helpers, route GETs.
Effort:      M
Test:        VIEWER GET `/api/vendors` omits email/phone/uploadToken. VIEWER POST `/api/vendors` → 403.

ID:          A2-08
Title:       Delivery-failure webhook updates another tenant’s NotificationLog
Severity:    Medium

Fix sketch:  Correlate via Resend `email_id` stored on NotificationLog.meta at send time. File: `webhooks.js`, `email.js`.
Effort:      M

ID:          A2-09
Title:       User.email is globally unique — a person cannot join two tenants
Severity:    Medium
Evidence:    `schema.prisma:124` `email String @unique`. Invite of an existing email 409s (`users.js:37-40`).
Impact:      An estimator who works with two GCs cannot be a MEMBER of both. They will sign up a second personal email or share passwords. Not a data-bleed, but it pushes customers toward account sharing (which is a data-bleed).
Fix sketch:  Unique `(orgId, email)` membership table; login picks org or uses an org switcher. Large change — product decision.
Effort:      L
Test:        Invite existing email into org B → membership created, not 409.

ID:          A2-11
Title:       allOrgs API tokens and webhook endpoints are platform superusers
Severity:    Medium
Evidence:    Schema comments `schema.prisma:270-273,318-319`. CLI `--all-orgs` (`scripts/create-api-client.js`, `create-webhook-endpoint.js`). `apiAuth.js:65-67` allows any org when `allOrgs`. `webhookDispatcher.js:51-56` `OR: [{ orgId }, { allOrgs: true }]`. UI cannot create these (`integrations.js:12-14,85`).
Impact:      One leaked platform token (printed to an SSH session, CI log, or Quill env) reads every customer’s vendors and signed PDF URLs. By design, but it is the highest-value secret in the product and is not in a vault recipe.
Fix sketch:  Document as owner-only; store hash-only (already); add lastUsed + alert; prefer per-org tokens for Quill. Optional: IP allowlist. Files: operator runbook, `apiAuth.js`.
Effort:      M
Test:        Existing `api-v1.test.js` “403 when a token is used against another org” must stay green; add a test that `allOrgs` token is rejected when `revokedAt` set.

ID:          A2-12
Title:       Vendor email uniqueness is application-level only
Severity:    Medium
Evidence:    No `@@unique([orgId, email])` on Vendor. Import and apply check `findFirst` (`import.js:130-132`, `apply.js:78-83`). Two concurrent POSTs can create duplicates; webhook then matches both (A2-01).
