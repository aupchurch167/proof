## A1-03 re-proof (PRIMARY) — **Verified**

**r1 hole:** email-link exception was “any `googleId` exists.” A `googleId` hit auto-set `emailVerified: true` without checking `profile.email === user.email`. After `PUT /me` to a victim inbox, the attacker’s own Google button (old email + same `googleId`) returned tokens and flipped the squat verified. Victim Google against that row also got tokens and kept the attacker’s `googleId`.

**This branch:**

```189:226:server/src/routes/auth.js
    if (user) {
      // googleId is not enough after an email change: Google must still own
      // the address currently on the row (A1-03).
      if (String(user.email || '').trim().toLowerCase() !== profileEmail) {
        return res.status(409).json({
          error: 'This Google account is no longer linked to this email. Sign in with your password or verify the new address.',
        });
      }
      if (!user.emailVerified) {
        user = await prisma.user.update({
          where: { id: user.id },
          data: { emailVerified: true, emailVerifyToken: null },
          include: { organization: true },
        });
      }
    } else {
      const byEmail = await prisma.user.findUnique({
        where: { email: profile.email },
        include: { organization: true },
      });
      if (byEmail) {
        // Email-link only when the inbox is already verified. A leftover
        // googleId on an unverified row must not auto-verify.
        if (!byEmail.emailVerified) {
          return res.status(409).json({
            error: 'An account with this email already exists. Verify your email or sign in with your password.',
          });
        }
```

`profileEmail` is `String(profile.email || '').trim().toLowerCase()` (`auth.js:182`). Email-link no longer has a `!byEmail.googleId` escape.

### Required cases

| # | Case | Result |
|---|---|---|
| 1 | Unverified password, no `googleId` (X-04) | **409**, no `accessToken` / `refreshToken`, `googleId` stays null, `emailVerified` false, **zero** `Session` rows. Official test + probe. |
| 2 | User with `googleId` changes email via `PUT /me`, then Google with **old** `profile.email` + same `googleId` | **409**, no tokens. | 3 | Leftover `googleId` + victim Google against the squatted unverified address | **409**, no tokens. Squat `emailVerified` false. Attacker `googleId` **not** replaced. No row with the victim `googleId`. Official leftover test + probe. |
| 4 | Happy path: verified user, `profile.email` matches current email, `googleId` matches | **200**, tokens, same `user.id` / `orgId`, `emailVerified` true, `googleId` unchanged. Probe (official suite had email-link + create, not this exact `googleId` hit). Mixed-case Google email vs stored `CaseMix@Gmail.com` also **200**. |
| 5 | `auth.js` review: no `emailVerified: true` on a `googleId` hit without email match | **None.** The only `googleId`-hit write is inside `if (user)` **after** the normalized mismatch `return 409`. The other two `emailVerified: true` writes are (a) email-link, which 409s unless already verified, and (b) first-time Google create. |

Tried to break it after the fix:

| Case | Result |
|---|---|
| Case 2 then tenant API | 403 `EMAIL_NOT_VERIFIED` — A1-02 still holds |
| `googleId` hit, emails differ, Google email uppercased | 409, `emailVerified` stays false |
| Email-link verified password row (no prior `googleId`) | 200, attaches `googleId` |
| Leftover `googleId` + victim Google with **different casing** than the stored squat | Squat unchanged (unverified, attacker `googleId` kept). Email-link `findUnique({ email: profile.email })` is **not** normalized, so a case miss mints a **new** Google org (200 for a different `user.id`). Residual, not a takeover of the squat. |

**Residual:** email-link lookup uses raw `profile.email` (`auth.js:206`), not `profileEmail`. Postgres `User.email` is case-sensitive. If an attacker stores `Victim@Gmail.com` and Google returns `victim@gmail.com`, the victim gets a new tenant instead of 409. The squat row is not verified and not rebound. Same-case victim Google (the r1 attack) is 409. Pre-existing identity-split; not the send-back class.

**Test quality:** official suite now covers X-04, leftover-`googleId` self-verify, and victim attach. Happy-path `googleId` hit was only probed here.

## Per-finding verdicts (reconfirm)

### A1-01 — Refresh tokens cannot be revoked — **Verified** (no regression)

`Session` (`schema.prisma:149-162`) + `issueTokenPair` / `rotateRefreshToken` (`lib/sessions.js`). Logout revokes the family. Reset and admin user-delete call `revokeAllForUser`. Refresh JWTs still carry a random `jti`.

**Repro:** official logout → refresh **401**; reset → refresh **401**. Probe: valid refresh 200 and new ≠ old; stolen old after rotation **401**; replay then rotated token **401** (family kill).

**Residual (unchanged):** 15m access JWT still works after logout; `PUT /me` password change does not revoke; pre-deploy refresh JWTs are not in `Session` and 401.

### A1-02 — Email verification never enforced — **Verified** (no regression)

## Migration review

A1-03 (`a6bfaae`) did **not** touch Prisma. The only B02 migration remains `server/prisma/migrations/20260920160000_add_sessions_and_invite_hash/migration.sql` (reviewed in r1):

- Additive: nullable `inviteTokenHash` / `inviteTokenExpiry`, new `Session` table, indexes, FK `ON DELETE CASCADE`. `inviteToken` plaintext is not dropped.
- Backfill hashes pending plaintext invites; expiry is `createdAt + 48h`. Idempotent. No Session backfill (old refresh JWTs 401 until re-login).
- Prisma wraps the file in one transaction. Failed `migrate deploy` rolls the file back. No data-loss. Rollback still `DROP TABLE "Session"` + drop the two columns/index.

## Merge vs send-back

**Merge PR #12.** A1-03 is Verified. Do not send back.

Reasons to merge:

1. All five A1-03 re-proofs hold. The r1 probes that issued tokens and set `emailVerified: true` now 409 with the squat still unverified.
2. Official suite **22 / 262** green, including the two new regressions that encoded the send-back hole.
3. X-02–X-04, T-02, L-02, V-01, O-03 still pass. Adjacent probes for the other eleven IDs match r1.
4. `auth.js` has no remaining `googleId`-hit path that auto-verifies when Google’s email does not match the row.
5. A1-03 added no migration. Prior additive Session/invite migration is unchanged.

Not send-back:

- Case-sensitive email-link (`profile.email` vs stored casing) can mint a **new** Google org. It does not verify or rebind the squat. Same class as “identity split,” not “unverified signup becomes a durable identity on the attacker’s tenant.”
- Documented residuals (signup body shape, `NODE_ENV` aliases, 15m access, UUID portal links until rotation) are unchanged from r1 and were not merge-blockers then.

**Do not patch auth in this verify PR.** If a later batch wants email uniqueness to be case-insensitive, normalize on write and look up with `profileEmail`. That is out of scope for B02 merge.
