## Per-finding verdicts

### A1-01 — Refresh tokens cannot be revoked — **Verified**

**Original:** 7-day refresh JWT with `{id, orgId}` only; logout was `localStorage.removeItem`; password reset cleared `resetToken` only.

**This branch:** `Session` (`schema.prisma:149-162`) stores `tokenHash` + `family` + `expiresAt`. `issueTokenPair` (`lib/sessions.js:12-25`) persists a SHA-256 hash. Refresh JWTs include a random `jti` (`utils/tokens.js:15-20`) so two logins in the same second do not collide. `rotateRefreshToken` (`sessions.js:35-65`) rotates, and reuse of a revoked/expired token kills the **family**. `POST /api/auth/logout` (`auth.js:280-302`) revokes the family (or all sessions if only an access token is sent). Password reset calls `revokeAllForUser` (`auth.js:506`). Admin user-delete does too (`users.js:159`). Client logout POSTs the endpoint (`AuthContext.jsx:57-75`).

**Repro (official):** login → logout → `/auth/refresh` **401**. Reset password → old refresh **401**. Passed (`b02-auth-portal.test.js:233-271`).

**Tried to break it:**

| Case | Result |
|---|---|
| Valid refresh | 200, new refresh ≠ old |
| Stolen old refresh after rotation | **401** |
| Replay then use the rotated token | **401** (family kill) |
| Refresh after logout | **401** |
| Refresh after password reset | **401** |
| Refresh after admin DELETE `/users/:id` | **401** |
| Access token after logout | **200** on `/auth/me` (15m access is not a session) |
| `PUT /me` password change (same password) | refresh still **200** — not in the finding’s test |

**Residual:** access JWTs live until `exp`. Profile password change does not revoke. Pre-deploy refresh JWTs are not in `Session` and 401 (called out in the fix PR). No HttpOnly cookie (A1-07, out of scope).

**Test quality:** official cases assert 401 after logout/reset, not just “logout 200.” Missing: rotation-reuse / user-delete (probed here).

### A1-02 — Email verification never enforced — **Verified**

**Original:** signup issued tokens with `emailVerified: false`; no route read the flag as a gate.

**This branch:** `requireVerified` / `authenticateVerified` (`middleware/auth.js:29-58`). Every session router except `auth` imports `authenticateVerified as authenticate` (vendors, users, org, settings, import writes, integrations, reports, audit, …). Allowlist matches the batch: auth, portal, apply, webhooks, health, import **templates**, v1 (API-token auth).

Unverified → `403 EMAIL_NOT_VERIFIED`. `/auth/me` and `resend-verification` stay on `authenticate` only.

**Repro (official):** signup → `GET /api/vendors` **403** + `EMAIL_NOT_VERIFIED`; `/auth/me` 200; resend 200; verify-email → vendors 200. Passed.

**Tried to break it — unverified access token against should-be-gated surfaces:**

| Route | Status |
|---|---|
| GET `/api/vendors`, `/cois`, `/users`, `/organization`, `/organization/usage`, `/settings`, `/integrations/api-keys`, `/reports/compliance`, `/audit`, `/notifications`, `/reminders/upcoming`, `/replies`, `/requirements`, `/compliance/overview` | **403** `EMAIL_NOT_VERIFIED` |
| POST `/api/import/preview`, `/api/import/vendors` | **403** `EMAIL_NOT_VERIFIED` |
| GET `/api/v1/orgs/:orgId/vendors` with the **session** JWT | **401** `unauthorized` (hashed as an API token, not found) |
| GET `/api/import/template/vendors` and `/cois` | **200** (static CSV, intended) |
| GET `/api/health` | **200** |

An unverified user **cannot** mint an API key (`/integrations` is gated), so they cannot reach v1 either. Existing keys minted *before* this deploy by an unverified admin would still work on v1 — v1 is API-token auth, intentionally not `requireVerified`.

**Residual:** `PUT /api/auth/me` is not gated (needed for profile / the verify banner). Combined with A1-03 this is how the send-back hole starts (email change), not a tenant-API bypass by itself.

**Test quality:** official test hits vendors + me + resend + templates + post-verify. Adjacent routes were only probed here.

### A1-03 — Google links to unverified password accounts — **Partially fixed**

**Original:** `findFirst({ OR: [{ googleId }, { email }] })` then write `googleId` + `emailVerified: true`. X-04: unverified password `a@gmail.com` + Google as that email must not return tokens.

**This branch (what works):** email-link is refused when `!emailVerified && !googleId` (`auth.js:195-199`). Official X-04: **409**, no `accessToken`, `googleId` stays null. Verified password row still links (200). Existing `googleId` login still works (200). Passed (`google-auth.test.js:108-132` + probes).

**This branch (what is broken):** the email-link exception is “any `googleId` exists,” not “`googleId` already matches this Google account” (the first `findFirst` already handled a match). And if `googleId` hits, an unverified row is **auto-re-verified** without checking `profile.email === user.email` (`auth.js:210-216`).

**Break 1 — leftover `googleId` + unverified victim email (victim clicks Google):**

Attacker row: `email=victim@gmail.com`, `emailVerified=false`, `googleId=gid-att-*` (attacker’s). Victim Google (`gid-victim`, email victim). Result: **200 + tokens**, `emailVerified` flipped **true**, `googleId` **kept as the attacker’s**. Victim is dropped into the attacker’s tenant.

**Break 2 — self-verify after email squat (attacker clicks their own Google):**

1. Password user, verified, then attach `googleId=gid-self-*`.
2. `PUT /api/auth/me` → `victim-inbox-*@gmail.com` (200, `emailVerified: false`, verify mail sent to an inbox they do not own).
3. `POST /api/auth/google` with **the same** `googleId` and Google email still equal to the *old* address.

Probe result:

```json
{
  "googleStatus": 200,
  "hasTokens": true,
  "bodyEmail": "victim-inbox-1789920659068@gmail.com",
  "bodyVerified": true,
  "dbEmail": "victim-inbox-1789920659068@gmail.com",
  "dbVerified": true,
  "dbGid": "gid-self-1789920659064"
}
```

Attacker is now a **verified** admin at the victim address, can use tenant APIs, and still has the password. The victim cannot sign up (`User.email` unique). This is A1-02 + A1-03 + A1-11 undone in one Google click.

**Not just a test-case fix for X-04.** The password-unverified path is real. The `googleId` branches were not.

**Send-back fix (do not apply in this verify PR):**

- Email-link only if `emailVerified === true`. Drop `&& !byEmail.googleId`.
- On the `googleId` hit: do **not** set `emailVerified: true` unless `profile.email === user.email` (or refuse the login / require the verify link after an email change).
- On email change, consider clearing `googleId` or storing it as pending until the new inbox is proved.

**Test quality:** X-04 asserts 409 + no token + `googleId` still null. Missing: unverified + leftover `googleId`; `googleId` path after `PUT /me` email change.

### A1-04 — Invite tokens never expire / returned by GET /users — **Verified**

**Original:** UUID plaintext, no expiry, `GET /users` selected `inviteToken`.

**This branch:** 32-byte hex, SHA-256 at rest, 48h expiry (`users.js:60-73`). Create response is `{ id, email, …, invitePending }` — no token. `serializeUser` (`users.js:14-24`) only exposes `invitePending`. Accept/info use `findInviteUser` (`auth.js:45-59`): hash **or** legacy plaintext, then require `inviteTokenExpiry` in the future.

**Repro (official):** GET `/users` JSON has no `inviteToken`; accept sets verified; expired accept **404**. Passed.

**Tried to break it:**

| Case | Result |
|---|---|
| POST `/users/invite` body | no `inviteToken`; DB `inviteToken` null, hash+expiry set |
| GET `/users` | `invitePending` only; no hash |
| Legacy plaintext, unexpired | invite-info **200** (expand fallback) |
| Legacy plaintext, expired | accept **404** |
| Consumed token | invite-info **404** |

**Residual:** plaintext column kept; unexpired pre-hash rows still accept the raw token until `createdAt+48h` (backfill) or the stored expiry. After that window they die. Intended expand.

**Test quality:** official GET assertion is `JSON.stringify ≉ /inviteToken/` (would also catch a leaked `inviteTokenHash`). Create-response omit was only probed here.

## Migration review

File: `server/prisma/migrations/20260920160000_add_sessions_and_invite_hash/migration.sql`.

- **Additive only:** two nullable columns on `User`, new `Session` table, indexes, FK `ON DELETE CASCADE`. `inviteToken` plaintext is **not** dropped.
- **Backfill:** `UPDATE "User" SET inviteTokenHash = encode(sha256(convert_to("inviteToken", 'UTF8')), 'hex'), inviteTokenExpiry = createdAt + 48 hours WHERE inviteToken IS NOT NULL AND inviteTokenHash IS NULL`. Matches `hashToken` (`apiTokens.js:15-17`). Scoped to pending invites. Idempotent. Pending invites older than 48h from `createdAt` stop working — intended.
- **Session backfill:** none. Old refresh JWTs 401 until re-login.
- **Locks:** `CREATE UNIQUE INDEX "User_inviteTokenHash_key"` is a blocking index (not `CONCURRENTLY`). Fine on a small pre-launch `User` table; would stall writes on a large one.
- **Mid-fail:** Prisma wraps this file in a single transaction (no `CONCURRENTLY` / no non-transactional DDL). A failed `migrate deploy` rolls the whole file back. The new app will not boot against a half-applied B02 schema from this script. If someone ran the SQL by hand statement-by-statement, login would crash after the columns landed but before `Session` existed.
- **Data-loss:** none. Rollback is `DROP TABLE "Session"` + drop the two columns/index. Hashed-only invites become un-acceptable after rollback (plaintext null) — documented on PR #12.

## Merge vs send-back

**Send back PR #12.** Do not land until A1-03’s `googleId` branches are closed.

Reasons to send back:

1. Official X-04 is only the no-`googleId` password row. Adjacent probes issued tokens and set `emailVerified: true` on an unverified address the Google account does **not** own.
2. That is the original finding’s impact (“unverified signup becomes a durable identity”) plus a tenant-gate bypass. Not fail-closed.

Reasons the rest of the batch is otherwise ready (after the Google fix):

1. X-02–X-04 (the password case), T-02, L-02, V-01, O-03 pass and match the code.
2. Unverified users cannot operate vendors/import/integrations or present a session JWT as a v1 key.
3. Logout / reset / rotation-reuse / user-delete all 401 the refresh token.
4. Portal UUID/expiry/purpose are 401; vendor GETs do not echo `uploadToken`.
5. Apply UUID is 404; slug + plan cap work.
6. Migration is additive and transactional.

**Do not silently patch Google in a verify PR.** Re-open on `fix/B02-auth-portal`: email-link only when `emailVerified`; do not auto-verify a `googleId` hit unless `profile.email` still matches; add tests for leftover `googleId` and for “change email then Google with the old account.”
