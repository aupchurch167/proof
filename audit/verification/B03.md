### A3-02 — Vendor delete hard-deletes COIs and Spaces objects — **Verified**

**Original:** single + bulk `deleteFile` each `pdfPath`, then `prisma.coi.deleteMany`, then vendor `deletedAt`. MEMBER could wipe history. NotificationLog FK was expected to 500 or succeed depending on logs.

**This branch:** `softDeleteVendorsAndCois` updates COI `deletedAt` then vendor `deletedAt` inside `prisma.$transaction`. No `deleteFile` / `getSignedUrl` import on the vendor router. Default COI access hides deleted rows; ADMIN may pass `includeDeleted=true`.

```293:344:server/src/routes/vendors.js
async function softDeleteVendorsAndCois(tx, { ids, orgId, now = new Date() }) {
  await tx.coi.updateMany({
    where: { vendorId: { in: ids }, orgId, deletedAt: null },
    data: { deletedAt: now },
  });
  return tx.vendor.updateMany({
    where: { id: { in: ids }, orgId, deletedAt: null },
    data: { deletedAt: now },
  });
}
```

**Repro (official):** MEMBER `DELETE /api/vendors/:id` with COI + NotificationLog → 200, `deleteFile` not called, COI row kept with `deletedAt`, log still `coiId`d, default GET 404, MEMBER `includeDeleted` 404, ADMIN `includeDeleted` 200 + `pdfPath`. Bulk same. Passed.

**Tried to break it:**

| Case | Result |
|---|---|
| MEMBER single + bulk delete | **200**. `deleteFile` 0. Bulk reported `2 vendor(s) deleted` when a third id was another org. |
| Cross-org id in bulk body | Org B vendor stayed live (`deletedAt` null). No IDOR. |
| VIEWER / REVIEWER delete | **403** |
| Soft-deleted vendor list / GET | Hidden / **404** |
| ADMIN `GET /api/cois/:id/pdf?includeDeleted=true` | **200** signed URL for `spaces/keep-me.pdf` — file is recoverable |
| MEMBER same includeDeleted PDF | **404** |
| Portal JWT after vendor delete | **404** (`loadPortalVendor` requires `deletedAt: null`) |
| NotificationLog | Row intact, `coiId` still set (vendor path does not touch logs) |

**`DELETE /api/cois/:id` residual (asked check, not a regression of the A3-02 claim):** still hard-deletes the row and calls `deleteFile` (`cois.js:314-321`). Probe: **200**, row gone. `NotificationLog.coiId` became **null** — the live FK is `ON DELETE SET NULL`, not Restrict as the original write-up guessed, so this path does **not** 500 when logs exist. Batch only covered the vendor path. Documented on the fix PR and in `audit/findings/new.md`.

**Incomplete hide (follow-up, not send-back):**

- `GET /api/v1/orgs/:slug/cois` and `GET .../cois/:id/document` do **not** filter `deletedAt`. After vendor soft-delete, the same APPROVED COI was **listed** (`leaked=true`) and the document endpoint returned **200** with a signed URL. Session UI hides it; the public API still serves it to that org’s token.
- `GET /api/organization/usage` vendor count drops after delete; **COI count does not** (`used: 2` before and after). `evaluatePlanLimit('coi')`, import COI cap, and portal upload cap all count every row. Vendor quota frees; COI quota does not until someone hits the residual hard-delete.
- `POST /api/reports/export-pdfs` looks up by id + orgId with **no** `deletedAt` filter (attempted to download the soft-deleted key). Useful for recovery; also means a known id is still exportable.

**Test quality:** official cases assert `deleteFile` not called, row retained, log retained, ADMIN-only peek. They do not cover v1, usage, VIEWER, or cross-org bulk (probed here).

### A3-04 — Cron jobs are in-process and not durable — **Verified**

**Original:** four in-process `CronJob`s; no lock; two Node processes double-email. Token refresh is not catch-up safe.

**This branch:** each sweep (`expiration`, `chase`, `tokenRefresh`, `weeklySummary`) wraps the body in `withAdvisoryLock` on a **new `pg.Client`** (not a Prisma pool checkout) using stable int8 keys (`730301`–`730304`). `pg_try_advisory_lock`; if false, return `{ acquired: false, sent: 0 }` and do not send.

```12:34:server/src/lib/advisoryLock.js
async function withAdvisoryLock(lockKey, fn) {
  const client = new Client({ connectionString });
  await client.connect();
  try {
    const res = await client.query('SELECT pg_try_advisory_lock($1) AS locked', [lockKey]);
    // ...
```

**Repro (official):** two overlapping `runExpirationSweep` → one `acquired`, `[sent]` sorted `[0, 1]`, one NotificationLog. Held lock on a raw `pg.Client` → sweep `acquired: false`, email not called. Passed.

**Tried to break it:**

| Case | Result |
|---|---|
| Overlapping `runExpirationSweep` | one acquired, one log |
| Overlapping `runChaseSweep` | one acquired, one `UPLOAD_CHASE` |
| Other session holds `LOCK_KEYS.expiration` (other-machine / other-process stand-in) | sweep no-ops, `sent: 0` |
| Same session holds `chase` while expiration is free | chase no-ops; keys are independent |
| Two dedicated connections `pg_try_advisory_lock(tokenRefresh)` | first true, second **false**; `runTokenRefresh` `{ acquired: false, refreshed: 0 }` |

Session-level advisory locks are cluster-wide, so a second process on another machine talking to the **same Postgres** no-ops the same way as the second in-process call.

**Connection-pool edge case (residual, not send-back):** the lock is held on the dedicated Client’s backend. That is correct for a direct `DATABASE_URL`. If production uses Neon’s **pooled** (PgBouncer transaction-mode) URL, each query on that Client can be assigned a different server backend: `unlock` may not hit the locker, and a second process can acquire. Schema has no `DIRECT_URL`. Deploy must point cron/locks at a session-sticky / unpooled URL.

**Residual (already in STATUS):** still in-process; no boot catch-up; a missed 08:00 waits until the next tick (expiration windows still catch up; token refresh does not). Official suite does not cover chase/token/weekly overlap (chase + token probed here).

### A2-12 — Vendor email uniqueness is application-level only — **Verified**

**Original:** no unique on `(orgId, email)`. Concurrent POSTs could create duplicates.

**This branch:** partial unique index `Vendor_orgId_email_active_key` on `(orgId, email) WHERE deletedAt IS NULL`. Create / update / apply map `P2002` → **409** (`VENDOR_EMAIL_CONFLICT` on session routes). Confirmed in Postgres after `migrate deploy`.

**Repro (official):** parallel create → statuses `[201, 409]`, one live row; reuse after soft-delete → 201 new id. Passed.

**Tried to break it:**

| Case | Result |
|---|---|
| Three-way parallel create | `[201, 409, 409]`, live count **1** |
| Soft-deleted + new live same email | **201** (official + implied by reuse) |
| `PUT` live vendor to another live email | **409** `VENDOR_EMAIL_CONFLICT` |

| `POST /api/apply/:slug` existing email | **409** |
| Apply race | `[201, 409]`, live **1** |

Prisma reports the conflict as `(`orgId`,`email`)`; `isVendorEmailConflict` matches any unique target containing `email`. Loose if another email unique ever lands on that write, but correct for this index.

**Migration backfill (asked check):** dropped the unique index, inserted three live rows with the same `(orgId, email)` staggered `createdAt`, re-ran the CTE, recreated the index.

### A6-04 — Graceful shutdown does not stop cron — **Verified**

**Original:** SIGTERM closed HTTP + Prisma; `CronJob.stop()` never called. A new 08:00 tick could start during drain; an in-flight sweep could be killed by the 10s fuse.

**This branch:** `startCronJobs` returns the four handles; `shutdown` calls `stopCronJobs(cronJobs)` **before** `server.close`. `job.stop()` prevents further ticks. There is **no** `running` flag / wait for an in-flight sweep. 10s `process.exit(1)` remains.

```23:36:server/src/index.js
function shutdown(signal) {
  console.log(`${signal} received. Shutting down gracefully...`);
  stopCronJobs(cronJobs);
  server.close(async () => {
    console.log('HTTP server closed');
    await prisma.$disconnect();
    process.exit(0);
  });
  setTimeout(() => { process.exit(1); }, 10000);
}
```

**Repro (official):** `startCronJobs` length 4, all `running`; `stopCronJobs` → all `!running`. Passed.

**Process-level:** spawned `node src/index.js` (port 4010). Boot logged all four jobs. `SIGTERM` → `SIGTERM received. Shutting down gracefully...` / `HTTP server closed` / `Database connections closed` / **exit 0**. Did not hit the 10s fuse. `stopCronJobs` is not separately logged; the call is on the only path before `server.close`.

**Residual (already in STATUS / batch):** shutdown does **not** wait for an in-flight sweep. Original finding’s test (“SIGTERM during a mocked long sweep waits, then exits 0”) is not implemented. An 08:00 send that has already passed `pg_try_advisory_lock` can still be cut by the 10s fuse (partial NotificationLog). `job.stop()` only prevents a *new* tick after the signal. Batch work item was `job.stop()` on SIGTERM, not the full wait. Not send-back.
